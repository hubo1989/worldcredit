## 1. 目标与完成标准

用户应能准确回答：我和家人的哪张卡拥有某项权益，本期分配多少、已经使用多少、预约占用多少、还剩多少、何时重置，以及今天需要领取、预约或使用什么。

优惠和权益在用户侧统一为“机会”，保留底层不同语义：优惠是附带适用条件的活动，权益是持卡资格下的服务或额度，领取的券是有独立有效期的一笔配额。关注活动、确认领取、预约服务和实际使用必须分别记录，不能用同一个成功提示代替。

### 1.1 已确认范围

| 阶段 | 交付项         | 完成后可执行的用户动作                                                          |
| ---- | -------------- | ------------------------------------------------------------------------------- |
| P0   | 修正现有问题   | 查看真实活动、正确识别名下卡、看到真实操作结果；修复权限、周期与使用校验缺陷    |
| P1   | 我的权益台账   | 按本人／家庭成员、个人卡查看当期额度、已用、剩余、重置日，记录、撤销、更正使用  |
| P1   | 我的可用机会   | 聚合优惠与权益，按今天可用、即将到期、待领取、已用尽筛选，卡片详情展示相关机会  |
| P1   | 权益日历与提醒 | 查看月底失效、年度重置、活动截止、领取截止与预约窗口；忽略或延后提醒            |
| P2   | 消费达标任务   | 手动维护年费减免、开卡礼、月消费任务的合格笔数／金额，查看缺口和发放窗口        |
| P2   | 领取与预约管理 | 记录待领取、已领取、已预约、已使用、已失效状态，保存银行 APP 操作指引或官网入口 |

P1 支持录入和提醒静态领取截止／预约窗口；完整领取、预约和额度占用状态机在 P2 接通。P1 的“待领取”来自已确认资格及已开放窗口，只提供银行入口、忽略和延后，**不提供“记录已领取”，也不承诺领取后自动消失**；P2 开放领取记录后才按事实自动解除。需要领取激活的配额在 P1 保持 pending_claim，不误判可用。P2 依赖 P1 的账户、配额和审计基础，不另做一套用量模型。

### 1.2 本轮不做

- 最佳刷卡推荐、优惠自动叠加计算、全市场自动活动采集。
- 银行登录、代用户报名、实际抢券、实际预约、支付、自动核销或自动取消银行订单。
- 用账单总额推断合格消费，自动计算年费达标，交易明细持久化及自动任务进度。
- 积分／里程账户、收益估值、卡片保留建议、邮件或 webhook 通知渠道。
- 跨持卡人的共享权益池、跨用户家庭邀请体系、R2 凭证附件上传。
- 修改账单、还款、额度共享、邮箱账单等既有业务语义。

## 3. 术语与业务口径

| 名称                 | 含义                                                           |
| -------------------- | -------------------------------------------------------------- |
| 定义／规则版本       | 一项优惠或权益的适用条件、周期、配额、有效期及来源的已发布快照 |
| 权益账户 Account     | 某个持卡人基于某项定义拥有的资格；按个人卡或同一持卡人共享     |
| 关联卡               | 该账户可以实际使用的信用卡；必须属于账户的持卡人               |
| 配额批次 Cycle       | 一个周期或一笔发放形成的额度；有独立起止日期和规则版本         |
| 使用记录 Usage       | 一次真实使用的当前投影；可更正或撤销，不物理删除               |
| 额度流水 Ledger      | 使用、预约占用、释放、撤销、期初核对等不可变更事件             |
| 机会 Opportunity     | 账户、配额、条件和个人状态计算出的可行动项目                   |
| 消费任务 Task        | 一个持卡人名下的消费条件和奖励计划，包含独立周期及手动进度     |
| 履约记录 Fulfillment | 应用内对领取、奖励到账或预约的记录，不代表银行操作已执行       |

### 3.1 归属与共享

1. 默认每张个人卡独立建账户。同一产品的两张卡不会自动共享额度。
2. 银行明确按同一持卡人共享时，管理员可建立一个 `holder` 账户并关联其多张符合条件的卡。界面显示“本人多卡共享”，余额只扣一次。
3. 一个账户只有一个持卡人。本轮不把家庭成员合成一个共享余额。
4. 同一实际卡对同一定义最多绑定一个当前有效账户，防止同时落入独立及共享账户而重复计数。
5. 银行信用额度模式、账单合并模式与权益共享无推导关系。
6. 账户有不可变的历史归属快照。已发生使用的账户不能直接换持卡人；应归档后为新持卡人另建账户。
7. 关联卡冻结或注销后保留记录，停止出现在“今天可用”；撤销错误记录、处理既有预约仍可执行，但必须有权限。

### 3.2 数据可信度

- `unverified`：遗留内容或模型候选，尚未人工确认。
- `user_confirmed`：用户明确核对或手工提供的规则／余额，不等于官网已验证。
- `official_verified`：管理员保存可核对的官方来源、摘录和确认时间。

来源可信度与个人资格分开。官方活动存在不能证明某位用户已获邀、已达标或已领取。条件未知时显示“需确认”，不计入首页“今天可用”，不发送催促消费的推送。用户可提交自己的确认和备注，不能把私人的确认升级为全局官方验证。

无结束日期仅表示“未设置截止日”，不能自动标“长期有效”。只有规则明确 `open_ended=true` 才可展示“长期有效”。

## 4. 角色、数据范围与操作权限

| 操作                                       | 管理员                       | 成员                                           |
| ------------------------------------------ | ---------------------------- | ---------------------------------------------- |
| 维护共享优惠／权益定义、审核候选           | 可执行                       | 不可执行                                       |
| 查看权益账户与机会                         | 自己创建／管理持卡人的范围   | `auth_user_id` 绑定自己的持卡人范围            |
| 初始化账户、调整共享范围、处理无归属旧记录 | 管理范围内可执行             | 不可把账户绑定给其他人；可确认自己的余额与资格 |
| 记录、更正、撤销使用                       | 管理范围内可执行，记录代办人 | 自己持卡人范围内可执行，记录实际操作者         |
| 创建手动任务、记录领取和预约               | 管理范围内可执行             | 自己范围内可执行                               |
| 关注、已读、忽略、延后、推送偏好           | 仅自己的个人状态             | 仅自己的个人状态                               |

具体范围由服务端 session 派生。新接口不能依赖“admin 跳过 memberGuard”获得所有账户的访问权；每次对账户、卡、任务、记录、履约对象按同一 actor 验证。管理员共享目录权限不扩展成私人账户全站查询权限。

成员可有多个绑定持卡人，聚合只覆盖这些持卡人。请求中的 `holder_id`、`card_id` 是筛选条件，不是授权依据。空绑定返回清晰空态，不退化为全站查询。不能通过分页计数、标题、备注、导出、提醒正文泄露其他范围的数据。

## 5. P1：我的权益台账

### 5.1 入口与结构

复用 `/benefits`，页面标题为“我的权益”。管理员默认管理范围，成员默认本人；顶部提供持卡人、银行、实际卡和状态筛选。筛选状态写入 URL，返回详情后可恢复。

一个账户展示一行，同持卡人共享账户展示关联卡列表。按卡筛选时仍是同一个共享余额，不能复制累加。展示：

- 权益名称、类型、银行、产品、持卡人、实际卡尾号；名称沿用个人卡覆盖逻辑。
- 本期起止、规则时区、下一重置日，或单次配额的截止日。
- 本期总额、已使用、已预约占用、可用余额及单位。
- 资格状态、余额是否待核对、来源及最近确认时间。
- 记录使用、使用历史、查看来源；管理员另有维护、归档入口。

支持次数、金额、同时限制次数和金额、明确无限额四种口径。金额按原币种最小货币单位保存，展示原币种；本期不做跨币种权益余额合计。无限额显示“次数不限”，不写成 0；额度 0 是合法的“当前无额度”。未知余额不展示成 0 次已用／全额可用。

### 5.2 初始化与变更

从实际卡列表选择一张或同持卡人的多张卡，再选择适用的已发布定义。零权益用户能从空态完成初始化。成员可提出待核实记录和确认个人资格，不能修改共享目录；管理员可代建。

规则更新发布新版本：已开始的周期和已发放配额保留原版本；默认从下一周期生效。活动提前终止需要显式录入终止时间与原因，立即影响今后的可用性和提醒，但不删除历史使用。需要即时调整当前余额时另记调整事件，不能改模板后悄悄重算旧记录。

领取／预约窗口可为固定日期，也可逐周期录入；后者为当前配额批次保存已核对的绝对时间，不把首月日期复制到下一月。缺具体时间显示待补充；调整窗口要有原因并更新对应提醒。

### 5.3 周期与日期

- 支持自然日、自然周（周一开始）、自然月、指定月日开始的年度、核卡／激活周年、单次有效期。
- 周期按规则 IANA 时区计算，日期窗口为 `[start_on, end_before)`；界面可显示结束前一天。
- 月底锚点每次从原始锚点计算，不能连续 `setMonth`；2 月 29 日周年在非闰年取 2 月最后一天，后续闰年恢复 29 日。
- `issued_on`、`activated_on` 与应用录入时间不同。周年规则缺锚点时显示“待补充核卡／激活日期”，不假设 `created_at`。
- 使用日期采用规则当地日期，默认今天，可补记过去，禁止未来日期。过去日期必须落在当时有效的配额批次内。
- 月中／年中首次建模可以创建当前名义周期，实际可用起点取有证据的规则与个人资格生效日，不能被迫等到下期，也不能据此假定此前具备资格。
- 不能证明过去资格的补记进入“待核对”，由有权用户确认；非 active 卡不能伪造为今天可用。
- 不做未声明的滚存。旧周期有剩余，重置后也不加到新周期。

### 5.4 记录使用

表单包含账户、实际卡、配额批次、当地使用日期、次数／金额、备注。默认选最早到期的可用配额；多批次时显示明确选择，本期不自动跨批次拆分一笔使用。

提交必须校验实际卡归属和适用性、有效窗口、资格、配额、金额币种及数据版本。实际卡不可为空，即使是银行级活动也要选一张符合条件的卡。

前端生成并复用 `idempotency_key`，网络超时重试复用原 key；成功后清空。相同 key 和相同输入返回第一次结果，不重复扣减；相同 key 配不同输入报冲突。先得到服务端成功再关闭表单并提示，失败保留输入。

### 5.5 使用历史、更正与撤销

- 历史记录可筛日期、卡、操作者和状态；显示发生时间、登记时间、备注和所有更正链。
- 更正日期、卡或次数／金额时，服务端原子反冲旧事件并写入新事件；旧记录不可消失。
- 由已完成预约产生的使用记录必须从“预约／履约纠正”进入，原子同步预约状态、实际卡、配额、使用及提醒；通用使用纠错入口不得单独修改或撤销这类记录。
- 跨周期更正需同时检查两个周期。目标周期不足时整次失败，原记录仍有效。
- 备注更正也记录操作者和原因，但不产生额度增减。
- 撤销需要确认和原因；撤销过的记录只读保留，不再次返还。恢复使用应新建记录，不删除撤销历史。
- 已结束周期的撤销仅修正该周期历史，不增加本期余额。
- 错误补记可更正；超过权益有效期后不能新增“今天使用”，但可按真实过去日期补记或撤销。

### 5.6 历史无归属记录

旧 `benefit_usages` 无个人归属，全部保留原表并标待归属；不能因为同款卡当前只有一个人就把历史事实猜成确定。管理员可查看并指定唯一归属、实际卡、使用日和理由，一条源记录最多映射一次。

旧 `promo_usages` 有有效 `card_id` 且归属可验证时可迁入对应账户；卡已删除或缺关联的进入待归属。源记录、原 ID、原始字段和迁移映射保留。

成员只看到自己账户“存在待核对历史用量”的提示，不见无归属记录的备注。当前周期可能受未归属记录影响时，余额标“不完整”；在归属处理或用户明确确认期初余额前，不计为确定可用。不把旧表和新流水重复求和。

期初核对保存统计截至日期及未逐笔登记的耗用。后续归属历史记录时，用户须确认该条是否已包含在核对总额中；包含时只将同额耗用从“期初”转成“有明细使用”，余额不再扣一次。无法确认就暂停归属并要求核对，不能按日期自动猜测。

## 6. P1：我的可用机会

### 6.1 入口

复用 `/promos`，标题“我的可用机会”，类型切换为“全部／优惠／权益”。保留现有路由。`/benefits` 侧重余额与历史，`/promos` 侧重下一步动作，两页复用账户、可用性和操作组件。

卡片详情增加“可用机会”，同时显示该卡关联的优惠和权益，默认最多 3 条并可进入完整列表。首页显示“今天可用 N 项”，N 由同一服务端计算，不能使用目录总数。

### 6.2 筛选和排序

筛选：持卡人、实际卡、银行、场景分类、类型、状态、关键词。URL 参数固定为 `holder`、`card`、`bank`、`category`、`kind`、`status`、`q`，服务端采用对应 snake_case DTO 并校验。

状态筛选：

| 状态           | 语义                                                             |
| -------------- | ---------------------------------------------------------------- |
| 今天可用       | 日期、资格、至少一张 active 关联信用卡、未占用余额等均已确认满足 |
| 即将到期       | 今天起 7 天内结束、仍有余额或待办；月度剩余额度在月底失效也包含  |
| 待领取         | 领取窗口已开启且该用户有资格，尚未记录领取；P1 可来自手动确认    |
| 已用尽         | 已用和预约占用后可用额度为 0；显示“使用完”或“预约占用中”的原因   |
| 需确认         | 内容、资格、周年锚点或余额不完整，或复杂条件未结构化             |
| 未开始／已失效 | 未到使用期、已结束或已归档；默认隐藏，可主动筛选                 |

可用状态、履约状态和关注状态独立；一个已领取的券仍可能已经过期，一项活动被关注不代表已报名。

默认顺序：今天截止的可行动项 → 3 天内截止 → 7 天内截止 → 当前可用 → 待领取 → 需确认。显式打开历史后，未开始、已用尽、已失效置后。同级按截止日、名称、账户 ID 稳定排序，不做未经定义的价值评分。

一项账户在聚合列表出现一次；多卡共享不重复。不同持卡人的同项权益分别展示。首页数量按 distinct 可用账户计数，多配额批次不重复；任务和提醒数量另列，不能混入“今天可用”。计数与分页用同一筛选快照。

### 6.3 适用规则

- 产品级定义必须命中实际卡的 `card_product_id`；银行级优先用稳定 `bank_id`。
- 旧记录只有 `bank_name` 时进行确定的别名映射并人工确认，禁止 `includes` 模糊认领其他银行。
- 卡组织、等级、地区、支付渠道、商户白名单、邀请制等条件未建模或未知时保留原文并要求确认，不能默认满足。
- 规则可声明周几有效；非有效日期不标今天可用。
- 当前冻结、注销及贷款类卡不成为可用机会。历史仍可查看。
- 关注存于用户级状态，仅控制收藏和个人提醒，不改变资格和配额。

### 6.4 操作和异常反馈

动作名称必须描述实际效果：记录使用、记录已领取、记录预约、查看银行入口、关注／取消关注。打开银行网站只提示“已打开入口”，不能标为报名或领取成功。

来源链接仅允许 `https:` 或明确允许的 `http:` 官方链接；不执行用户录入的脚本、任意应用 scheme。银行 APP 暂保存名称和操作路径，展示为可复制指引。

区分加载中、无卡、无适用定义、筛选为空、接口失败、余额待核对、版本冲突和权限变化。刷新失败不能把列表默认为空或显示成功。

## 7. P1：权益日历与提醒

### 7.1 日历

新增 `/benefits/calendar`，从台账、机会页和首页提醒入口进入。默认本月，支持月历／按日期列表切换；移动端优先日期列表，月历选择日期后查看事件。沿用持卡人／卡筛选。

事件包含：额度失效、周期重置、活动截止、领取截止、预约开放、预约截止；P2 补入任务截止、预计发放窗口、已预约服务时间。只显示有依据的日期；缺日期进入待补充，不凭模型补造。

显示事件类型、当地日期／时间、规则时区、对象、持卡人／卡、剩余额度和建议动作。采用规则日期放置截止／重置事件，具体预约时间换算展示用户时区并附原时区。不合并不同人的事件。

### 7.2 提醒生成

默认应用内启用；Web Push 需用户开启该类提醒，且已有有效订阅。新增配置不自动开启 email/webhook。

| 类型           | 默认节点                     | 生成前提                           |
| -------------- | ---------------------------- | ---------------------------------- |
| 月／年配额失效 | 提前 3、1、0 天              | 剩余可用额度 > 0，资格与余额已确认 |
| 周期重置       | 当地重置日                   | 新周期已可用；同一重置事件一次     |
| 活动／券截止   | 提前 7、3、1、0 天           | 有可用额度或未完成领取动作         |
| 领取截止       | 提前 3、1、0 天              | 有领取资格且未记录领取             |
| 预约开放／截止 | 开放时；截止前 1 天及当天    | 有资格且没有已确认预约             |
| P2 任务截止    | 提前 7、3、1、0 天           | 尚未达标或奖励动作未完成           |
| P2 预计发放    | 发放窗口开始、结束仍未收到时 | 仅提示“预计／待确认”，不自动记到账 |
| P2 预约服务    | 提前 1 天及当天              | 预约未取消、未使用，实际时间已设置 |

无法执行的项目不催用：已用尽、失效、冻结卡、待核实信息不会产生“马上消费”类提醒。缺数据可以进入应用内待核对列表，不推送敏感的猜测结论。

### 7.3 已读、忽略和延后

提醒状态按登录用户保存；管理员已读不影响成员。

- 已读：处理当前提醒，不等于权益已使用。
- 忽略：屏蔽该对象当前周期／截止事件，保留日历；业务截止或规则版本发生实质变化后可产生新事件。
- 延后：支持明天 09:00、三天后 09:00、自定义时间，按用户时区解释；超过对应有效截止时拒绝并建议忽略。
- 恢复：清除忽略或延后，重新按当前业务状态判断。
- 备注、普通使用次数变化不会反复清空忽略；用尽后对应催用待办自然消失，P2 的已领取事实会解除对应领取待办。P1 静态领取窗口只能由用户忽略／延后，不假装已有领取事实。

提醒身份包含类型、对象、周期／配额批次及业务日期版本；同一个阈值节点和推送通道只排队一次。读过提前 7 天提醒不屏蔽后来提前 1 天的新节点；忽略整个事件则屏蔽该事件剩余节点。具体键见技术附录。

### 7.4 发送与时区

权益扫描采用 UTC 每 15 分钟一次的独立 Cron 分支；现有每日账单扫描只在原 `0 9 * * *` 分支执行，不能因新频率变成每 15 分钟发账单提醒。

权益提醒默认当地 09:00，遵守用户 quiet hours。新配置读取 `user_preferences.reminder_config.opportunities`；缺省用户时区为 `Asia/Shanghai`，可修改。规则时区和用户时区分别保存。

扫描生成待发送记录，发送前再次核对权限、余额、领取／预约状态、忽略和延后。安静时段顺延到下一个允许时段，若届时业务已结束则取消。没有订阅只保留应用内事件，不能记录为已发送。

按订阅记录发送结果，410／404 的过期订阅按现有方式清理。重试只发未成功的订阅，退避 15 分钟、1 小时、6 小时，最多 4 次且不越过业务截止。Web Push 服务接受不等于用户设备收到；界面和日志用“已提交推送服务”。服务端崩溃存在重复投递窗口，使用稳定 tag 合并，不承诺严格一次送达。

## 8. P2：消费达标任务（手动进度）

### 8.1 入口与任务字段

新增 `/benefits/tasks`，台账中显示“任务”入口，个人卡详情可创建带卡片预填的任务。

类型：年费减免、开卡礼、月消费达标、自定义。字段：持卡人、单卡或同一持卡人多卡范围、标题、条件、币种、统计周期、截止日、预计发放窗口、奖励、领取方式、来源和备注。

周期支持单次、自然月、年度及核卡／激活周年；复用 P1 时间工具。年费周期不自动套自然年；核卡日期不明时不得启动周年倒计时。

### 8.2 条件表达

支持最多 3 组 OR 条件，每组最多 3 个 AND 指标：

- 合格消费累计金额，原币种。
- 合格消费笔数，可附“每笔至少 X 元”。
- 手动完成确认项，例如已激活、已报名；需要用户明确确认。

示例：“5 笔各满 388 元，或累计消费 3000 元”是两组任选一，不是把两组条件同时要求满足。

不建通用表达式语言。商户、渠道、排除交易、退款等复杂条件保存说明，用户录入的是自己确认的合格进度。界面明确“手动确认，未与银行流水自动核验”。

### 8.3 进度录入与缺口

用户输入当前周期累计合格金额、各门槛对应的合格笔数、完成确认项、统计截至日期和备注。采用绝对快照，不用“+500 元”之类累加输入，防止重试重复累计。

金额和笔数允许 0，禁止负数；不同货币不自动折算。多指标的笔数按指标 ID 分开，不把低门槛笔数直接用于高门槛。

每次修改产生不可变更的进度事件并保存 revision。更正可降低进度，例如退款后减少，显示“进度已下调”，不能始终 max(old, new)。两设备冲突返回当前值让用户重录。

缺口按每组逐项计算，展示“再消费 1200 元，或再完成 2 笔每笔至少 388 元”。达标只表示手动进度满足已录入规则，不能自动标为银行确认。

### 8.4 达标、发放与奖励

任务生命周期与奖励生命周期分开：未开始 → 进行中 → 手动进度已达标；截止后不达标为未完成，达标后奖励仍可待发放／待领取。

- 预计发放窗口可为明确日期范围，或统计周期结束后的次月第 X—Y 日。2 月没有的日期取该月最后一天，并显示计算依据。
- 预计日期到达仅提醒，不增加权益额度。
- 奖励分为“配额奖励”和“非配额结果”。配额奖励实际收到后才建立带有效期的批次；非配额结果只保存履约事实。同一任务周期同一奖励只记录一次，不能通过更换类别重复登记。
- 配额奖励有定义模板时关联其账户；没有模板的券可建立仅该持卡人可见的私人券定义，不写入全局目录。
- 年费减免或无法量化的礼品属于非配额结果，可没有权益账户和配额，只保存实际确认日、结果及备注，不伪造可消费额度。
- 退款导致已达标变不达标时保留已到账事实并显示“资格需复核”；不能自动撤销银行已发放奖励。确认银行追回后按纠正流程处理。
- 当前周期结束后保存完整快照，下期重新开始，不能把已达标数值复制到下期。

## 9. P2：领取与预约管理

### 9.1 领取

区分三类动作：普通权益激活／领取、任务奖励实际到账、券领取。记录实际日期、有效期、领取入口、备注及操作者。

普通权益领取只解锁已有配额，不额外加一份额度。任务奖励到账创建一笔新配额；`grant_only` 权益在未到账前没有常规额度，防止把月度默认额度和奖励额度重复叠加。

状态按时间和记录派生：未开放、待领取、已领取、已失效、已取消。过了领取期不能点击“今天领取”；可按真实过去日期补录，注明补录。

误记领取可撤销，但如果已关联使用或预约，必须先撤销／更正这些记录，或由管理员完成整体纠正；不允许负余额或让既有使用悬空。

### 9.2 预约

填写实际卡、配额批次、服务时间和时区、地点／服务商、外部预约参考号（可选）与备注。保存的是用户已在银行或服务商处完成的预约记录，应用不代为预约。

- 草稿不占用额度；记录已确认预约才占用配额。
- 预约确认从可用额度转为 reserved，不计作已使用。
- 记录已使用时，reserved 原子转为 used，不再多扣一次。
- 直接使用与预约转使用必须经过同一额度服务。
- 服务时间必须落在配额可使用窗口，不能把年底过期额度预约到下年后继续使用，除非规则明确允许并保存该许可。
- 改服务日期跨配额批次时按两批次原子处理，目标不足则保留原预约。

### 9.3 取消、失效及额度结算

取消应用记录不代表银行取消成功。确认取消时必须选择银行额度结果：已退回、已扣除／罚扣、尚不确定。

| 结果         | 本地额度与状态                                             |
| ------------ | ---------------------------------------------------------- |
| 已退回       | release reserved，预约标已取消；额度仅在原批次仍有效时可用 |
| 已扣除／罚扣 | reserved 转为 used，并注明取消损耗，不冒充已享用服务       |
| 尚不确定     | 标“已取消，额度待确认”，保留占用，提醒核对                 |

到服务时间不自动宣称已使用；未确认的结果进入待核对。配额到期后不再可用，历史的预约／已用状态保留，系统不猜测银行是否退款或罚扣。到期逻辑不能生成新的有效额度。

## 10. 来源、审核和目录维护

统一候选流程：选择银行／卡产品 → 提供官方 URL 或粘贴文本 → AI／人工整理候选 → 展示字段、来源摘录和缺失项 → 管理员勾选复核 → 发布规则版本 → 持卡人确认个人资格。

- 采集失败应返回具体错误；不得退回模型记忆后默认为有效。
- 模型候选一律 `unverified`，不会自动加账户、额度、首页数量或提醒。
- “官网已核实”要求可访问官方域名、可对应的摘录、规则有效期及人工确认；标题相似不构成核实。
- 抓取只读、超时、限制响应大小，继续复用现有 `site-fetch` 约束；不下载执行网页内容。
- 有使用／预约／迁移映射的定义只能归档，不能硬删除级联历史。
- 私人券只允许当前持卡人范围查看，不能泄露到共享目录和其他用户筛选数量。

## 11. 兼容、历史和发布约束

1. 新增表、字段及 RPC，不删除现有数据；旧返回字段至少保留一个兼容版本。
2. `getAllMyBenefits` 旧的产品级数字保留为受限范围聚合，新增账户明细并明确其不能作为个人扣减依据；新 UI 全部改用新接口。
3. `recordBenefitUsage` 旧签名转兼容适配器：能唯一定位账户和实际卡时调用新服务；多解时返回 `AMBIGUOUS_ACCOUNT`，不得随意选第一张。
4. 所有新使用只写新账本，旧表冻结为历史源；不能双写再重复统计。
5. 旧导出入口继续可用，内部迁至新 RPC。权益／优惠历史分别输出真实归属和状态；待归属历史仅管理员可导出并明确标识。
6. 发布按增加存储 → 本地迁移演练 → 兼容 API → 新 UI → 用户核对 → 移除旧写路径推进。代码回退保留新增数据，禁止回退时 DROP 新账本。
7. 本轮文档工作不执行提交、推送、远程迁移或部署；实施时按用户当时的授权操作。

## 12. 非功能与体验要求

- 使用现有 Workers、D1、命名 RPC、ObsidianUI，不引入 MUI 或新后台服务。
- 私人数据查询在 SQL 层限定范围；分页默认 30、最多 100，日历单次最多 92 天；避免每账户一次查询。
- 日期、金额、时区、枚举、长度、URL 和 ID 参数显式校验；所有 SQL 参数化。
- 错误保留可行动 code：未登录、无权、参数非法、版本冲突、超额、已过期、需确认、归属不明确；日志不打印 session、推送密钥或敏感备注。
- 每次写入都有 actor、请求 key、时间和理由；界面显示实际发生与登记时间。
- 触控目标至少 44px，支持键盘和焦点恢复；错误与状态不能只靠颜色。
- 验证 360／390／768／1280 宽度，长中文、多卡共享、金额与单位不溢出。
- `.op` 是唯一视觉源；同步注册表、行为契约、重建脚本和候选导帧。不得用更新截图基线掩盖业务错误。
